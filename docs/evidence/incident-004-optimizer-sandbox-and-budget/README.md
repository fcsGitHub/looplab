# 事故报告 004：OptimizerPort 首次接入的沙箱豁免缺口、静默反射失败与预算过冲

日期：2026-09-24　|　发现者：实现迭代中的直接检验（非用户报告）　|　状态：已修复并有测试覆盖

## 背景

按设计 §5.3/§6.8 接入 OptimizerPort（GEPA 0.1.4 后端）。三个缺陷耦合在一起，
使第一、第二次"看起来完成"的试炼实际无效或险些无效：

### 缺陷 1：run token 未传入后端子进程 → 反射调用全部静默失败

`OptimizerService.runBackendRound` 生成 Python 后端子进程时没有把
`LOOPLAB_OPT_TOKEN` 放入子进程环境。后端所有反射 LLM 调用带空 Bearer →
代理 401；又因 GEPA 引擎 `raise_on_exception=False` 吞掉每次异常，
优化器在"零反射信号"下空转，烧掉 81 次本地评估（每次都是真实子进程沙箱执行）。

**修复**：子进程 env 注入 run token（它是后端获得的唯一凭据，模型密钥仍不出
控制进程）；后端侧加连续失败熔断（≥3 次反射失败 → 停止迭代、如实上报），
并把每次反射失败写入 `out_dir/errors.log`，杜绝静默。

### 缺陷 2：批量评估的预算过冲

GEPA 的 `max_metric_calls` 停止检查只在批间进行。设预算 80、验证批 6 例：
计数到 78 时下一批整批执行 → 84 > 80。合同校验（`completeRun` 拒绝任何
超支 run）按设计拦下了它——内核守卫工作正常，但适配器需要**执行前预检**
（`metric_calls + len(batch) > cap` 则先停），避免到达边界的批次被整个作废。

**修复**：`backend.py _check_metric_budget` 改为预检；内核侧严格校验保留不变。

### 缺陷 3：venv 解释器下沙箱误伤标准库 → 内部评分全 0

后端运行于 `.venv-gepa`（venv）。venv 中 `sys.prefix` 指向 venv 目录，
而真实标准库位于 `sys.base_prefix`（miniconda）。`candidate_runner.py`
的审计钩子 stdlib 豁免只比对 `sys.prefix`，于是候选子进程在安装钩子后
**所有标准库文件打开被拒**，GEPA 内部评估全部得 0 分——优化器毫无信号，
把种子候选原样当作"最佳改进"输出，且内部 val_score=0.0 这一异常
（装箱效率不可能是 0）在第一次"成功"试炼里没有触发任何告警。

EvalBroker 的既有链路未受影响，因为它以 base python 启动评测器
（`sys.prefix == base_prefix`）；只有 venv 启动的新链路踩中。

**修复**：`_stdlib_prefixes()` 同时放行 `sys.prefix` 与 `sys.base_prefix`
（标准库可信，封存目录/工作区外路径仍一律拒绝——A10 语义不变）；
`seal-suites.ts` 重新 provision 运行副本。

## 诚实记录

- 第一次"成功"试炼（opt_0854239bf2b9，12 次真实反射调用、$0.023）因缺陷 3
  的全 0 评分**作废**：提案被标 REJECTED，证据文件删除，run 标记 FAILED。
  它的 reflection 调用计入了预算账本（真实花费），计入总开销。
- 检验手段：直接以适配器评分基线源码，FFD 效率应 ≈0.93–0.97、劣策略 ≈0.73；
  修复后验证通过，评分有区分度。
- 沙箱边界未被削弱：本次改动只放行解释器自有标准库；A10（封存标签窃取）
  等沙箱测试在修复后全量回归通过。

## 教训

1. 跨进程凭据传递要有端到端断言（401 不应表现为"静默无信号"）。
2. 优化器的内部指标是验收信号：全 0 / 恒定值应触发显式失败而非"完成"。
3. venv 布局是 Windows 单机上最常见的 base/prefix 分裂来源，沙箱豁免
   必须同时覆盖两个前缀。
